# PhysMaster v9.3 Complete Replacement

基于本次提供的 `PhysMaster-v9.3-full.zip` 完成主流程替换。版本标识：`9.3-complete_replacement`。这是非官方扩展版本，不代表上游团队发布。

## 实际替换了什么

此前的 `core/repair_agent.py`、`core/research_lifecycle.py`、`utils/failure_classifier.py` 只有文档字符串；`v93_pipeline` 等函数没有接入 Supervisor 的真实节点执行。另有仅根据非空文件就把状态标为 PUBLISHED 的旁路函数。本版移除这些重复入口，将下列路径接入普通节点和报告补交节点：

1. Supervisor 并行派发初始 Theoretician 节点。
2. 节点输出统一进入 `NodePipeline.process`，修正可验证的本节点路径、登记文件。
3. Critic 评审；无有效评分或缺少明确评审字段时，对同一份输出重新评审。
4. 程序核对硬性参数、代码绑定、执行回执、声明文件及当前子任务交付要求。
5. FailureClassifier 分类；RepairAgent 对工程／交付问题生成有具体诊断的新修复任务，真正提交工作进程执行。
6. 修复使用新的 `node_N` 目录，再次经过 Critic 和程序核对。旧节点、文件和原始评审保留。
7. 生成五项评分、反向更新 MCTS、记录知识与网页数据。未验收经验继续带有 UNACCEPTED 标记。
8. 搜索结束后，仅从选中且已验收的分支核对文件哈希、归档并发布到 `final/`；网页显示实际发布结果。

评分发生在搜索中，用于排序；最终发布发生在分支选择以后。不能先把所有尝试的文件标成已发布，再计算分数。

## 失败怎样处理

| 实际情况 | 自动行为 |
| --- | --- |
| 工作进程异常 | 新修复节点重新执行；进程池损坏时重建 |
| 最后一次 Python 执行失败 | 携带错误和原输出，修复后执行并重新评审 |
| 空 JSON、交付失败、文件漏交或声明未核实 | 新节点补交和核对；不会仅凭磁盘上有文件自动验收 |
| 参数／程序证据问题 | 按原合同修复，不能放宽锁定参数 |
| Critic API／评分／协议异常 | 对原节点重评，不重复求解 |
| 科学评审提出方法问题 | 交回 MCTS 常规研究修订，不假装已被工程修复 |
| 重试上限用尽 | 保留失败，显示原因，不能强制通过 |

`repair_status` 表示自动修复状态，不代表研究是否完成。失败父节点即使拥有成功的修复后继，也不会被改成已验收。

## 研究阶段与范围

支持 EXPLORATION、MODEL_BUILDING、SIMULATION、VALIDATION、FINALIZATION。Clarifier 可明确填写 `research_stage`；旧合同缺少该字段时，按子任务类型和描述做保守推断。推断只是任务分类，不是完成证明。

研究阶段与 `solving/evaluating/repairing/finished` 等执行状态分开。`revise` 不再自动等于 VALIDATION。求解器和 Critic 都收到相同阶段范围：早期数值节点不会被要求提交后续报告；当前子任务明确要求的文件仍必须核对。硬性参数在所有阶段和修复中始终有效。最终完成检查仍核对整个合同，不能靠阶段划分漏掉交付。

## 评分

| 分项 | 权重 | 依据 |
| --- | ---: | --- |
| science | 50% | Critic 的有效科学／方法评分 |
| artifact | 20% | 声明文件与实际格式、哈希核对记录 |
| execution | 10% | 最后一次 Python 执行回执；不把无记录当成成功 |
| compliance | 15% | 硬参数、代码绑定与程序证据核对 |
| communication | 5% | JSON、实质结果字段及非失败交付结构 |

不适用项重新归一权重；适用项缺少评分则综合分为 `null`，网页显示“未评分”。MCTS 内部需要数值时仍以 0 占位，但不会将它伪装成科学质量 0 分。科学通过／重做阈值仍只作用于 science；高综合分不能覆盖未解决问题和程序违规。

## 成果状态

`CREATED → REGISTERED → VERIFIED → PROMOTED → PUBLISHED`

登记扫描、声明核对、文件格式及哈希检查、选中分支归档、最终复制分别对应实际操作。只有非空文件不足以通过。下载时仍核对来源和哈希。`status` 保留旧页面所需的兼容字段，`state/lifecycle/state_times` 保存新状态及时间。

文件 VERIFIED 表示该文件通过基础核对，不等于节点已验收。PROMOTED 和 PUBLISHED 还要求节点验收及本次分支选择。一个任务可以部分完成，同时发布已验收子任务的文件；最终清单仍明确标为 partial。

## 网页

- 左侧研究设置与条件对话，右侧宽幅研究区。
- 五个视图：研究节点、成果交付、研究总结、运行时长、运行日志。
- 节点默认折叠：显示阶段、简短成果、状态、综合分和科学分。
- 展开后显示“做了什么／Critic 怎么看／学到了什么／证据与工具”、五项评分、决定调整原因。
- 显示修复来源、后继节点、后继结果、重评次数及用时；可点击跳转修复节点。
- 支持按研究阶段、待解决节点、已验收节点和修复链筛选。
- 轮目标仍可滚动；轮询保留折叠、滚动和焦点。
- 保留能力独立开关、Critic 阈值、硬参数、条件追加、暂停续研、总结下载和计时。

## 配置与调用成本

旧 `config.yaml` 无须添加字段也可启动；默认设置如下：

```yaml
repair:
  enabled: true
  max_node_retries: 1
  max_critic_retries: 1
```

两个上限均为 0～3 整数。每个初始节点默认至多新增 1 个修复节点；每个节点默认至多额外重评 1 次。每个新修复节点也需要求解、评审及知识整理调用，可能增加耗时和费用；这不是减少节点计算量的加速算法。底层 SDK 的网络重试独立计算。

修复在当前研究轮内完成。“本轮结束后暂停”和追加条件仍在轮间生效；正在修复时发出的条件会等这一轮结束后重新规划。完成后续研仍创建独立新任务、继承旧条件和摘要，不是恢复已经退出进程的执行栈。

报告专用补交仍由 `finalization.max_attempts` 单独限制；每次报告派发也经过同一修复控制器，因此实际报告节点数可多于该派发次数。

## 验证范围

见 `Test-report-v9.3.md` 和 `validation/`。测试使用离线模型桩，但真实启动 `run.py`、spawn 工作进程、Python 工具、CSV/PDF 生成、Critic 门禁、MCTS、归档发布；不是只检查函数是否能导入。

没有使用你的 DeepSeek/Tavily 密钥，没有完成真实 Windows 系统测试，没有重新计算太空跳伞的物理结论。网页通过实际 HTML/JavaScript 的 DOM 行为测试，未声称完成浏览器截图视觉验收。现有科学模型是否正确，仍需其本身的收敛、适用范围与独立验证。
