# v8.3.2 评审决定覆盖修复

适用于已安装 v8.3.2 的项目，可与 UTF-8、滚动补丁叠加。

## 修复内容

原代码在 Critic 缺少 blocking_issues 或报告关键问题时，会统一改为 to_revise；节点核对结果为 unchecked 时也会统一改为 to_revise。这会把本来更严格的 to_redraft 错误放宽。

现在两层检查都保留已有 to_redraft／reject；明确违反约束仍要求重做，未核对证据可把 complete 改为 to_revise，但不能把重做降为修订。原评分不改。

policy_reason 保留评分门槛原因并追加阻塞原因。新增 decision_adjusted 记录最终决定与模型原决定是否不同；integrity_adjusted 记录程序核对是否改变决定。threshold_adjusted 继续只表示评分门槛阶段是否改动决定。

## 使用

等本轮结束，在服务器终端 Ctrl+C 等待退出。备份后将本包解压到项目根目录，覆盖同名文件，随后用原启动方式重启；已装 UTF-8 补丁可继续用 start_physmaster_utf8.cmd。

不包含 config.yaml 或 outputs，不修改旧节点，不增加模型调用预算，也不能让空输出自动变成正确研究成果。

## 用户提供的零分节点

score_valid=true 表示评分格式有效。Critic 确实给出 reward=0；这不是缺失评分的默认占位。它看到空的解析输入，程序也没有获得可核对 JSON，因此不接受节点。

但“没有可解析结果”不等于已证明磁盘上没有任何文件，需检查节点目录和工具日志。工具循环上限为8轮；达到上限而没有任何非空 assistant 正文时，现有客户端会返回空字符串。这是空结果的一条可能路径，不能仅凭评审 JSON 确定它就是该节点根因。

## 验证

5项Critic设置／门槛测试、15项研究完整性测试通过，覆盖零分重做缺字段、非空阻塞问题、unchecked不能削弱重做、明确冲突与证据不足。修改的Python源文件通过语法检查。

没有在用户真实API环境重跑该节点；不改变物理模型或宣称该题已求解。
